# 数字后端日志综合实践

## 总结

后端日志分析应遵循“确认文件、保留副本、先筛选、再统计、最后判断”的顺序。关键词只提供候选位置，不能脱离上下文直接判定流程失败。

## 推荐目录

    review_01/
    ├── raw/
    ├── work/
    ├── result/
    └── backup/

- raw：保留原始副本，不修改。
- work：允许实验性修改。
- result：保存筛选和统计结果。
- backup：保存关键版本。

## 副本验证

    ls -lh raw/file work/file
    ls -li raw/file work/file

期望：

- 大小相同。
- inode不同。
- 两份文件彼此独立。

## 日志体检

总行数：

    wc -l file

错误候选：

    grep -ic 'error' file

警告候选：

    grep -ic 'warn' file

多关键词：

    grep -niE 'error|warn' file

## 生成统计文件

基本数据方向：

    输入日志 -> grep筛选 -> wc统计 -> awk加标签 -> 结果文件

示例：

    grep -ic 'error' file | awk '{print "ERROR:",$1}' >> keyword_count.txt

为什么管道中的wc没有文件名：

- wc从标准输入读取。
- 输出通常只有一个数字。
- awk只有$1，$2不存在。
- 如需文件名，可由awk输出固定文字。

## 筛选、排序和去重

保留行号的定位报告：

    grep -niE 'error|warn' file > error_warn_with_line.rpt

不保留行号的排序去重：

    grep -iE 'error|warn' file | sort -u > unique_error_warn.rpt

先去除行号再去重，是因为不同的行号会使正文相同的两行仍被判定为不同。

## Vim日志定位

- 使用:set nu显示行号。
- 使用/ERROR、/WARN搜索。
- 使用n、N移动匹配。
- 使用G检查文件末尾。
- 修改实验必须在work副本中进行。

## 结果判断原则

以下关键词可能产生误判：

    0 errors
    no error
    warning limit
    previous error count

正确流程：

1. 获取候选行。
2. 查看前后上下文。
3. 识别工具消息编号和严重等级。
4. 判断阶段是否继续或正常结束。
5. 再形成结论。

## Shell与EDA Shell

Linux Shell用于文件和进程操作。

EDA Shell通常基于Tcl，提供设计数据库命令。例如fc_shell和Innovus Shell。

不要因为提示符相似，就默认所有Linux命令都能在EDA Shell中直接执行。

## 安全检查

- 不对公共日志运行sed -i。
- 不在未确认路径上运行rm -rf。
- 不用>覆盖项目报告。
- 大型日志不直接cat刷屏。
- 退出EDA工具时区分正常exit和Ctrl+C中断。

## 自检

- 能建立raw/work/result/backup结构。
- 能生成带行号报告和排序去重报告。
- 能解释为什么关键词计数不等于真实错误数。
- 能证明原始副本未被修改。
